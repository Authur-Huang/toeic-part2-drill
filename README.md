# 多益聽力練習

多益 **Part 2（應答問題）** 與 **Part 3／4（對話與獨白）** 的手機練習 App。
可安裝到主畫面、可離線使用。

**題目與語音全部為本專案自製**，不含任何第三方測驗的版權素材。

| 部分 | 形式 | 選項 | 選項文字 |
|---|---|---|---|
| Part 1 | 看圖聽四句敘述 | 四選一 | **預設不顯示**（正式考試不印在題本） |
| Part 2 | 一句問答，約 8 秒 | 三選一 | **預設不顯示**（正式考試不印在題本） |
| Part 3／4 | 30–50 秒對話或獨白＋三題 | 四選一 | **顯示**（正式考試印在題本） |
| 圖表題 | Part 3／4 的一種，**每段最多一題** | 四選一 | 圖表在**播音前**就顯示 |
| Part 5 | 單句填空，純文字 | 四選一 | **顯示** |
| Part 6 | 一篇短文配四個空格（含插入句題） | 四選一 | **顯示** |
| Part 7 | 單篇／雙篇／三篇對照（含意圖題、同義字題） | 四選一 | **顯示** |

錯題會依 **1／3／7 天**自動排回來複習，連續答對三次才移出錯題本。
首頁有「只練圖表題的段落」，並單獨顯示圖表題的正確率。
音檔依 Part 分包下載，可以只帶走現在要練的部分。

---

## 為什麼從零做題庫，而不是收集現成的

1. **版權**：市面上堪用的多益聽力題（ETS 官方、各家出版社模擬題）都有版權，
   蒐集後整合進網站即為重製與散布。網路上找得到的免費多益音檔，多數本身就是他人非法上傳。
2. **容量**：內嵌音檔的單頁做法撐不住題量。25 題內嵌成單一 HTML 就已 8 MB，
   無法上傳、無法同步。改成 PWA ＋ 獨立音檔後，50 題只有 2.4 MB，而且可離線快取。

代價要講清楚：**TTS 比真人錄音乾淨**，沒有環境噪音與自然的語速起伏，
擬真度略低於正式考試。它適合衝題量與練題型反應；
純耳朵訓練建議另外搭配公共領域素材（VOA Learning English、LibriVox）。

## 題目設計

每題的兩個錯誤選項都對應一種真實的陷阱型態：

| 陷阱 | 說明 |
|---|---|
| Yes/No 回答 WH 問句 | WH 問句不能用 Yes/No 開頭回答，一定錯 |
| 重複原句單字 | 陷阱重複原字，正解通常換字 |
| 同音／同字不同義 | book（訂位／書）、change（改變／零錢）、run（跑／快用完） |
| 答錯疑問詞 | 問地點卻答時間、問頻率卻答時點 |
| 第三選項 | 選擇疑問句的正解兩個都不選 |
| 話題相關但沒回答 | 最危險的一種，聽起來很順 |

口音涵蓋多益實際使用的四種（美／英／加／澳），每題問答為不同說話者。

### 選項順序

題庫為了好寫，一律把**正解放在 `choices[0]`**；打散是在建置時做的
（`gen_audio.py` 的 `shuffle_item`）。重排依題號雜湊，**重跑建置不會改變順序**，
使用者的作答紀錄才不會對不上。解析裡的 `(A)(B)(C)` 標號會同步改寫。

⚠ 改動題庫後**一定要重生音檔**：三個選項是依序錄進同一支 mp3 的，
只改 JSON 不重生，聽到的順序會與畫面對不起來。
`build_site.py` 會擋下正解集中在同一位置（超過 50%）的建置結果。

## 閱讀題庫（Part 5／6／7）

重點是它**完全不碰音檔那一套**：`build/gen_reading.py` 沒有 TTS、沒有 ffmpeg，
跑起來是瞬間的事。純文字也代表**題庫可以放大而不影響 repo 體積**——
283 題（Part 5 二百、Part 6 三十二、Part 7 五十一）只有 103 KB，跟兩支 mp3 差不多。

- 題庫在 `itemsR/`，輸出到 `docs/itemsR.json`
- Part 5 是單題（`q`／`choices`）；Part 6／7 是 `passage` 配 `questions` 陣列，
  建置時會把兩種形狀歸一到同一個結構給 App 用
- 正解一樣寫在 `choices[0]`，建置時依題號雜湊打散，重跑不變順序
- Part 6 的空格在 `passage` 裡寫成 `___(1)___`，題目就叫「空格 (1)」；插入句題的選項是完整句子，題幹寫「選出最適合放這裡的句子」
- 「依題型練」依 `rGroup()` 分組：Part 5 拆到考點，Part 6／7 整個 Part 併成一項（逐篇列出會變成一堆四題的小項）
- Part 7 雙篇／三篇的文件分隔寫成 `【文件一】…`，App 會把這種行渲染成小標題
- ⚠ **文章裡不要用連續空白做欄位對齊**——HTML 會把連續空白摺成一個，表格會散掉。改用破折號分隔（`A — B — C`），換行了照樣讀得懂。

✅ **題目全部自寫。** 參考的只有公開的題型規格（Part 5 考詞性、時態、
介系詞、連接詞…），**沒有參考任何一份實際試題**。
⚠ 代價是沒有 ETS 的難度校準基準，難度可能偏移——
自製題的定位是**衝題量與練反應**，要相信分數請用官方試題。

## Part 1：圖是自己畫的 SVG，不是照片

這一點要跟使用者講清楚，否則會誤判自己的實力。

**做得到**：`is being V-ed` 與 `have been V-ed` 的分辨（Part 1 最大的考點）、
位置介系詞、畫面裡到底有沒有人、物品在但動作不存在。

**做不到**：`leaning`、`kneeling` 這類細緻姿態，
以及真實照片才有的曖昧地帶。示意圖會**乾淨到比真考簡單**。

→ 所以這批題的定位是**文法反射訓練**，不是 Part 1 模擬。
真正的 Part 1 手感留給官方試題。

圖用 `build/mk_part1.py` 組合出來——人形、地面、箱子都是可重複使用的函式，
風格才一致，也才畫得動。平均每張約 1.5 KB。

★ `p1-002`（人站在梯子上）與 `p1-023`（空梯子靠牆）**是刻意做的一對**：
同一個道具，差別只在有沒有人，正解就從進行式變成狀態描述。

## 圖表題（look at the graphic）

正式考試每份約 5 題，Part 3／4 各 2–3 題，**一段對話／獨白最多只出一題**。

### 出題鐵律：正解不能被念出來

> **聽到的是圖上的「一欄」，要答的是「另一欄」。**

如果對話裡直接說了 `Room 118`，那就只是普通細節題，圖表淪為裝飾。
必須是聽到 `leadership`（講題欄）→ 自己去表上查出 `Room 118`（房號欄）。
`build_site.py` 會把每一題圖表題的正解字串拿去比對該段對話原文，
**命中就中止建置**——這是最容易寫壞、寫壞了又看不出來的地方。

### 圖表怎麼存

不用圖片檔。表格類用 JSON 描述、App 端渲染 `<table>`（一張約 300 位元組）；
地圖、樓層平面、長條圖用 **inline SVG**（1–2 KB），以 `currentColor` 上色，
自動跟著深淺色主題走。好處是 repo 不變大、離線快取不受影響、手機上不會糊、
git diff 看得懂。

```json
{ "id": "p3-g01", "part": 3,
  "graphic": { "type": "table", "title": "…",
               "head": ["Time", "Session", "Room"],
               "rows": [["1:30 P.M.", "Team Leadership", "Room 118"]] },
  "questions": [ { "q": "Look at the graphic. …", "graphic": true, … } ] }
```

`"type": "svg"` 時改放 `"svg": "<svg …>"`。**圖表要在播音之前就顯示**——
正式考試圖表印在題本上，考生播音前就看得到；放到作答畫面才出現，練的是另一件事。

## 音檔的報題號

音檔流程比照正式考試：

- **Part 2**：`Number 7.`（旁白）→ 問句 → 三個選項依序唸出
- **Part 3／4**：`Questions 32 through 34 refer to the following conversation.`
  → 對話 → 每題 `Number 32. What is the problem?`
  **選項不唸**，正式考試 Part 3／4 的選項是印在題本上的

題號照正式考試的區間給：Part 2 為 7–31、Part 3 為 32–70、Part 4 為 71–100，
依題庫順序輪替。

⚠ **報題號那一段刻意不列入 `marks`**。Part 2 的 `marks` 四個位置對應
prompt／A／B／C，App 靠索引做「重聽選項 C」；多塞一格會讓全部重聽點位移。

## 重新建置

```bash
python build/mk_part1.py             # Part 1 題庫與 SVG（先跑這支）
python build/gen_audio1.py           # Part 1 音檔
python build/gen_audio.py            # Part 2 全部重生
python build/gen_audio.py p2-051     # 只補這個題號之後的
python build/gen_audio34.py          # Part 3／4 全部重生
python build/gen_audio34.py p3-004   # 只補這個題號之後的
python build/gen_reading.py          # 閱讀 Part 5／6／7（無音檔，秒完）
python build/build_site.py           # 複製 App 檔案、產生圖示、檢查
```

需要 `edge-tts`、`Pillow`，以及本機的 `ffmpeg`／`ffprobe`（路徑寫在 `gen_audio.py` 開頭）。

### 🔴 不要無謂地全量重生音檔

每支 mp3 重生後都是全新的二進位內容，**git 無法差分壓縮**——
全量重生一次，就在歷史裡永久多出約 18 MB，而且刪不掉（除非重寫歷史）。

只有改到「每一支都會變」的東西時才需要全量。到目前為止只發生過一次：
2026-08-29 加報題號。**一般的加題、改題一律走增量**（上面第二、四行指令）。

`.git` 目前約 34 MB，離 GitHub 的 1 GB 建議上限很遠，不需要現在處理。
若哪天題庫成長到 **400 題以上**、而且預期還要全量重生好幾次，
再考慮把音檔移出 `main`（改用 `gh-pages` 部署分支）。

🔴 **全量重生之後一定要把 `sw.js` 的 `AUDIO2`／`AUDIO34` 版本號加一**，
並同步改 `index.html` 的 `download()`。音檔是 cache-first 且不重驗的，
不換名的話，已經下載過的裝置會永遠播舊檔——而 `items.json` 走 network-first
會更新成新時間軸，結果是**新時間軸配舊音檔**，「重聽某一句」對不準，
畫面卻完全看不出異常。使用者要重新下載音檔，這是換掉音檔無法避免的代價。

⚠ **不要改用 Git LFS。** 它看起來正好為這種情況設計，但
**GitHub Pages 不解析 LFS 指標檔**——網站會拿到一串文字指標而不是 mp3，
音檔會全部播不出來。

## 已知的技術細節

- **串接後要校正時間軸**：mp3 用 `concat -c copy` 串接時，每個接縫都會累積編碼器補白。
  `gen_audio.py` 以實際總長等比例校正每段起點，否則「重聽選項 C」會愈後面愈歪。
- **Edge-TTS 每段前後自帶約 0.5 秒靜音**，不修掉的話選項間隔會變成設定值的三倍，
  聽起來比正式考試鬆很多。已用 `silenceremove` 濾掉。
- **紀錄只存在本機瀏覽器**，不跨裝置。跨裝置請用「複製錯題」帶去劃記本。
- **音檔快取名稱必須兩邊一致**：`index.html` 的 `download()` 寫入 `p2-audio-v1`／`p34-audio-v1`，
  `sw.js` 的 `audioCacheFor()` 必須讀同樣的名字。曾經因為 SW 只讀其中一個，
  導致下載好的 Part 3／4 音檔在離線時讀不到；`activate` 的舊快取清理也要同時保留這兩個名字。
- **Part 3／4 一段有三題**，紀錄的鍵是 `<段號>#<第幾題>`（例 `p3-001#2`），
  Part 2 則直接用題號。錯題複習時，Part 3／4 是整段重聽而非只出那一題。
